# OneSim v0.3 GPU benchmarks

**Reference machine.** MacBookPro18,1, Apple M1 Pro with a 16-core GPU and 16 GB unified memory,
macOS 27.2.1 (26B131), system Metal driver, Rust 1.100.0 with the release profile, wgpu 30.0.2
and Vello 0.12.0. The browser checks used headless Chrome 158.0.8127.36 and Swift 6.4.2 Wasm.

## Home and typography readback profile

Two interleaved runs per revision, each with 150 measured captures at 402 × 874 pt, 3× (1206 × 2622).
The before build included the instrumentation and the original readback. The after build also
avoided zero-initializing the output and used a vectorizable alpha check before copying opaque rows.
Times are ranges of the two runs' p50s in milliseconds.

| Home | After | 1.68–1.69 | 2.77–2.84 | 0.02 | 0.38–0.41 | 1.66–1.68 | 0.67 |
| Typography | Before | 5.29–5.49 | 4.60–4.62 | 0.03 | 0.73–0.76 | 2.60–2.62 | 1.07–1.08 |

Home's first frame had 3 sprite hits and 14 misses, followed by 2,550 hits and zero misses.
Typography had 4 hits and 11 misses, followed by 2,250 hits and zero misses. Counts were identical
with either readback. Home GPU capture is still slower than CPU capture on this machine. The
readback improvement matters to capture and leaves the interactive path's zero-readback blit intact.

## Workload measurements

Each backend ran in its own process per workload with 12 warm-up frames and 150 measured frames.
The harness prepares a scene and captures it, so times cover layout or scene construction through
RGBA readback. The scrolling workload advances a 250-row list by 85 pt per frame. Push/pop emulates
the navigation transition by sliding two laid-out screens. The form shows the keyboard and changes
the focused field's text. Glass uses four moving translucent panels and images use 18 rotated fills.
Animation moves 72 translucent circles with 60 Hz and 120 Hz time steps. The harness submits the
next frame as soon as the previous capture completes.

- **2×** is iPhone SE 3, 375 × 667 pt, 750 × 1334 px.
- **3×** is iPhone 17 Pro, 402 × 874 pt, 1206 × 2622 px.
- Over-budget counts are frames above 16.67 ms and 8.33 ms. Actual display drops require a visible presentation run.

GPU captures recorded zero backdrop fallbacks across the workload matrix. The 3× glass stack was the
only GPU workload with p95 above 16.67 ms. It spent a median 24.84 ms waiting for GPU work and readback.
The two 120 Hz animation workloads missed the 8.33 ms p95 budget. These are capture budgets. Sustained
60 Hz or 120 Hz desktop pacing and visible input-to-present latency still need an unlocked display run.

## Idle, presentation and stress

- Chrome ran the built SwiftUI showcase in CPU and GPU modes at both sizes. Each combination presented
  zero new frames over a 1.2 s idle interval. On GPU it then accepted input, retained the edited todo and
  focus through GPU device destruction, and added the todo after switching to Canvas 2D. Resize presented
  one frame at the requested size. An injected no-adapter result and malformed display list both produced
  a byte-identical CPU fixture frame.
- The native scheduler tests cover idle and coalescing. The macOS desktop was locked and the display asleep.
  Metal initialized with BGRA8Unorm, FIFO and a requested frame latency of two. The GPU swap chain skipped
  presentation. During momentum the window recorded at most four occlusion probes per second at both sizes.
  Scripted window snapshots used the GPU blit path, then switched to CPU within the same
  session. Captures show the SwiftUI slider updating before release and the Expo pan updating from
  `Pan: idle` to `Pan: 80,0` to `Pan: end 80,0`. These captures establish presentation-path and input
  correctness without a visible pacing or latency measurement.
- The Metal stress test rendered 1,050 frames with changing text, viewport, DPR, appearance and backdrop.
  The executor peaked at 121 live image resources and all 1,050 backdrop operations stayed on the GPU.
  Process RSS peaked at 69 MiB and finished at 64 MiB in a separate run of the test binary.
  A separate test destroyed the wgpu device, observed the typed device-loss error and replayed the same scene
  byte-for-byte on a fresh device. This exercises resource eviction and one outstanding headless readback at
  a time. A prolonged live GPU-memory or compositor queue trace remains unmeasured.

## Reproduce

```sh
cargo run --release -p onesim-render-gpu --example bench -- 150
cargo build --release -p onesim-render-gpu --example frame_bench
target/release/examples/frame_bench cpu 150
target/release/examples/frame_bench gpu 150
/usr/bin/time -lp target/release/examples/frame_bench gpu 150 iphone-17-pro glass-stack
cargo test -p onesim-render-gpu --test gpu rapid_updates_and_resizes_keep_resources_bounded -- --nocapture
cargo test -p onesim-render-gpu --test display destroyed_device_reports_loss_and_the_scene_can_be_replayed
scripts/build-web.sh examples/swiftui-showcase
node web/test/presenter.mjs --app
```

Pass a device and scenario to `frame_bench` to collect per-workload process statistics. Use
`SIMCORE_FRAME_STATS=1` on an unlocked desktop for native window stage timings.
