# Expo / React Native API coverage

What an Expo app can use under SimCore today, per platform, and what is still to do. One row per API
(component, native module or library). Pick any ⬜ / 🟠 / ⛔ row to work on: open an
[API request issue](https://github.com/MitchellSPeterson/SimCore/issues/new?template=api-request.yml) for it
(or take an existing one), and link the issue in the row's **Issue** column.

| Status | Meaning | Score |
|---|---|---|
| ✅ | Implemented: behaves as on a device | 1 |
| 🟡 | Simulated: works, backed by state the host controls (`modules.simulate`, session viewport, appearance) | 1 |
| 🟠 | Partial: works, with known gaps listed in Notes | ½ |
| ⛔ | Unsupported: calls print `SimCore: X is not supported` and throw/reject (never fake success) | 0 |
| ⬜ | Planned: not started | 0 |
| — | Not applicable on this platform (left out of the percentage) | |

**Android** ([#12](https://github.com/MitchellSPeterson/SimCore/issues/12)): there is no Android host yet. Android support needs Android view managers (`AndroidTextInput`,
`AndroidSwitch`, …) rendered with Material semantics, `Platform.OS === 'android'` constants in the guest, and
Android reference screenshots for the pixel-diff gate. The column tracks it from zero so work can be picked up
per row.

## Adding or changing a row

- Implementing a native module: add or update its entry in `frameworks/react-native/guest/modules.js`
  (status `implemented` / `simulated` / `unsupported`), put its name in backticks in the row's **Native**
  column, set the status, and run `node scripts/api-coverage.mjs`.
- Implementing a native view: render it in the host (`crates/simcore-render/src/layout/rn.rs`), add an iOS
  reference state and `shot` line for the pixel-diff gate (see CONTRIBUTING.md), and list its component name.
- Missing an API that is not listed: add a ⬜ row, open an issue, and link it.
